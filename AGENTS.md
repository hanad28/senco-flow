## Cloudflare production deployment

Cloudflare is the current primary host for `unisen.uk`. This app is deployed as a **Cloudflare Worker**, not a Pages project. TanStack Start builds through Nitro's `cloudflare-module` preset; the Worker serves both SSR and static assets.

### Live architecture

| Item | Value |
| --- | --- |
| Current Cloudflare account | `unisenofficial@gmail.com` via local Wrangler OAuth (**temporary personal ownership; migrate to the company account/team**) |
| Worker name | `unisen` |
| Wrangler config | `wrangler.jsonc` |
| Worker entry | `.output/server/index.mjs` (generated by `bun run build`) |
| Static assets | `.output/public` through the `ASSETS` binding |
| Observability | Enabled in `wrangler.jsonc` |
| Deployment method | Manual Wrangler CLI from this repo; no Cloudflare GitHub CI yet |

The same Worker has three Cloudflare custom-domain routes:

| Host | Behaviour |
| --- | --- |
| `https://unisen.uk` | Marketing landing page, whether signed in or signed out |
| `https://www.unisen.uk` | Same marketing landing page |
| `https://app.unisen.uk` | Clerk sign-in when signed out; dashboard when signed in |

Host classification lives in `src/lib/site.ts`; request/browser host detection and Clerk hand-off query detection live in `src/lib/hostname.ts`; the auth/marketing shell lives in `src/routes/__root.tsx`.

Important auth behaviour:

- Marketing CTAs navigate to `app.unisen.uk`; Clerk sign-in does not open on the marketing origin.
- Clerk `__clerk_*` hand-off query parameters that reach the marketing host are forwarded to the app host.
- After sign-in, users remain on `app.unisen.uk`.
- Signing out returns to `unisen.uk`.
- The auth page's **Back to unisen.uk** link always returns to the landing page.

### Cloudflare environment variables

There are two different mechanisms; do not confuse them:

**Build-time values** are loaded before `bun run build` and inlined by Vite:

| Variable | Required | Purpose |
| --- | --- | --- |
| `VITE_CLERK_PUBLISHABLE_KEY` | Yes | Clerk browser SDK |
| `VITE_CONVEX_URL` | Yes | Browser → Convex |
| `VITE_CONVEX_SITE_URL` | Recommended | Convex HTTP/site URL |
| `VITE_SITE_URL` | Yes for Cloudflare build | Must be `https://unisen.uk` |
| `VITE_APP_URL` | Yes for Cloudflare build | Must be `https://app.unisen.uk` |

The first three come from gitignored `.env.local`. `VITE_SITE_URL` and `VITE_APP_URL` are exported explicitly for production builds. Because `VITE_*` values are compiled into the output, changing a Cloudflare runtime secret does not update them; rebuild and redeploy.

**Worker runtime secrets** currently set on Worker `unisen` (names only):

- `CLERK_SECRET_KEY`
- `CLERK_PUBLISHABLE_KEY`

Inspect names safely with:

```bash
bunx wrangler secret list --name unisen
```

Never print secret values or commit `.env.local`. `CONVEX_DEPLOYMENT` remains local-only, and `CLERK_JWT_ISSUER_DOMAIN` belongs in Convex, not Cloudflare.

### Deploy to Cloudflare

Wrangler is already installed as a dev dependency and authenticated locally to `unisenofficial@gmail.com`. Confirm the active account before deploying:

```bash
bunx wrangler whoami
```

Build with the production origins, then deploy while preserving existing Worker secrets/vars:

```bash
set -a
source .env.local
set +a
export VITE_SITE_URL=https://unisen.uk
export VITE_APP_URL=https://app.unisen.uk

bun run build
bunx wrangler deploy --keep-vars
```

Do not deploy a build that was produced without the two production URL exports: production fallbacks can point at the Vercel demo. The package script `bun run deploy` is safe only when the current shell already contains all required `VITE_*` values; the explicit sequence above is preferred.

After deployment, Wrangler should report all three custom-domain triggers. Verify without exposing secrets:

```bash
bunx wrangler deployments list --name unisen
curl -I https://unisen.uk/
curl -I https://app.unisen.uk/
```

Expected result: HTTP 200 from both hosts. For runtime errors:

```bash
bunx wrangler tail unisen
```

### Local host split

The Lovable Vite config uses port `8080`:

```bash
bun run dev
```

| Local URL | Behaviour |
| --- | --- |
| `http://localhost:8080` | Marketing landing page |
| `http://app.localhost:8080` | Dedicated Clerk auth page / authenticated dashboard |

`app.localhost` resolves to loopback without editing `/etc/hosts`. If port `8080` is already occupied by this repo, use the existing dev server rather than starting another one on `8081`, because the default local site/app URLs are set to port `8080` in `src/lib/site.ts`.

### Clerk dashboard configuration

Clerk must allow these production origins/redirects:

- `https://unisen.uk`
- `https://www.unisen.uk`
- `https://app.unisen.uk`
- `https://app.unisen.uk/*` for redirects

Keep the local origins allowed as well:

- `http://localhost:8080`
- `http://app.localhost:8080`

The Clerk JWT template must remain named `convex` to match `convex/auth.config.ts`.

### DNS troubleshooting

Cloudflare manages the custom-domain DNS records. If `dig @1.1.1.1 unisen.uk A` returns Cloudflare addresses and a request using a known Cloudflare IP succeeds, but the browser reports `ERR_ADDRESS_UNREACHABLE`, check the local/router resolver before changing the Worker. One observed router returned only AAAA records while the Mac had no IPv6 default route. On this Mac, Wi-Fi DNS was changed to `1.1.1.1` and `8.8.8.8`, then the macOS DNS cache was flushed.

Also in Clerk dashboard (not env):

- JWT template named **`convex`**
